# dsh-plugins 升级至 dsh 0.1.7-rc.1：宿主、会话格式 V4、preset 载体与 Team profile

> 状态：**已批准（2026-09-24）并执行收口（2026-09-25–26）**。as-built、遗留未验证项与证据索引见
> `docs/dsh-v0.1.7-rc.1-upgrade-closeout.md`（票据 13）。子代理锚定（方案 A）由票据 14 落地并部署
> （2026-09-26：仓库 + 产物 + 部署位刷新；gate/real 零豁免、PTY 双形态 16/16）。

## Problem Statement

自研 TUI 当前运行在 dsh `0.1.5-rc.2` 上，上游已推进到 `0.1.7-rc.1`，中间跨越整个 `0.1.6` 代际。这一跳包含三类会让现有部署直接不可用的变更：会话日志升级到 V4 且不支持降级读；会话历史、agent 生命周期与 shell 沙箱接口异步化（现有同步读取接口先弃用、后改形）；Agent 预设与设置的载体变更（预设改由插件组合包声明安装、设置改存当前 Profile 的插件配置、旧设置文件只导入一次）。另有一个版本没有公开说明，且本机现有安装里没有发现面向用户的批量迁移命令。

使用者的诉求是跟上官方版本、并让新能力进入 TUI；但在动宿主之前必须回答"怎么迁、怎么验、最坏怎么退"。会话格式迁移不可逆，而新宿主对旧格式会话是只读还是打开即改写、迁移的真实形态是什么，都还没有实证。不取证就迁移，等于用一个无法回退的动作去赌未知行为。

自研 Preset 已裁决保留，其唯一不可替代的增量是二轮沙箱提权（bash 换用）。但它在 `0.1.7` 的载体形态不再成立——预设内容改为由插件组合包里的声明行承载。载体不迁移，部署位就加载不了它；Team Profile 里的 Preset 叠加实测（判断自研 Preset 与 Team 组合是否语义冲突）也依赖它先到位。

Agent Team 本轮开启，采用 Profile 划分：Team 是 Profile 层能力，开启后该 Profile 内普通委派工具在组合期被禁用。因此非 Team Profile 的委派与模型选择基线必须原样保留，两种形态的工具面与闸门口径必须分开。

此外，版本链已经拉长，部署位与仓库的一致性判定、宿主钉版断言、工具面期望与真实模型基线都建立在旧宿主上；不随宿主换代同步调整，闸门就会用错误基准给出错误的红绿。

## Solution

先取证、再迁移、后部署。

取证在临时前缀安装目标版本，不碰真实安装与部署位，交付：异步替代接口的确切签名、迁移工具的真实形态、新宿主对旧格式会话的读写行为、旧目录形态 Preset 是否仍被加载、无文档版本的实际变更面、以及回滚所需包的可重取性。取证变绿之前，不动迁移代码、不跑会话迁移。

宿主升级时两个工作 Profile 同步到位（宿主版本、Profile 插件树、部署位 Preset 一起走）；非 Team Profile 保持普通委派与模型选择基线，Team 用单独 Profile 承载。目标版本精确锁定，不跟随浮动标签；混合期以显式 CLI 覆盖切换，旧版本包留本地副本，回滚不依赖外部仓库。

会话格式迁移接受不可逆，但不保留"先不迁"分支：在首次启动新宿主之前完成静默、冷备与还原演练，明确丢失窗口与保留期；迁移执行按取证结论落地，抽样验证后再收口。

Preset 以仓库为唯一真源，目标载体改为与上游同构的声明形态；同步工具从"复制目录到部署位"改为"生成 Profile 侧产物"，并在写入真实部署位之前可 dry-run。该改造作为迁移第一工作项，先于 Team Profile 建立。

验证沿用既有回归闸门分层：宿主钉版与会话格式版本随宿主换代更新；仓库、清单与部署位的一致性拆成两层分别表述与豁免；工具面期望按 Profile 维度重建并逐行审阅；真实模型基线在新宿主上重采，采不了就显式记"未跑"，绝不跨宿主比较。

全部兼容项迁移完成、收口清单全绿后，统一把 Preset 产物与 Team Profile 落到部署位，并移除所有临时豁免。

## Implementation Decisions

**目标与范围**

- 升级目标精确锁定 `0.1.7-rc.1`，不跟随浮动标签；窗口内若正式版发布，收口后另开小步升级，不中途换靶。
- 两个工作 Profile 同步升级：宿主版本、Profile 插件树与部署位 Preset 一起到位；同步的是宿主版本，不合并两侧的委派模型选择口径。
- 稳定树与另一支旧安装点保持钉版，不在本轮目标内；旧版本包以本地副本留存，混合期以显式 CLI 覆盖切换。
- 先取证后施工：前置取证变绿之前，禁止迁移代码改动与会话迁移执行。
- 交付形态是文档加迁移改动；不自动提交、不自动推送。

**前置取证**

- 在临时前缀安装目标版本，使用独立缓存，不写真实用户目录、不改任何 Profile 与部署位。
- 交付六项事实：异步替代接口签名；批量迁移工具是否存在及其命令形态；新宿主对旧格式会话的读写行为；旧目录 Preset 是否仍被加载；无文档版本的包树差异；旧版本包的可重取性。
- 结论写回计划的未验证清单，作为后续票据的施工依据。

**会话格式迁移**

- 接受"迁移后旧宿主不可读"，且不再保留"先不迁"分支。
- 首次启动新宿主之前完成：静默所有写者、冷备会话目录到其外部并附文件数与指纹清单、用旧宿主做还原演练（打开若干代表会话，含一个带 Subagent 的）。
- 明确丢失窗口（快照之后新增的会话）与冷备保留期（至少到新宿主稳定走过一次正式版升级）。
- 迁移机制按 C0 取证结论执行（2026-09-24 已核实）：**没有面向用户的批量工具，也没有 dry-run**；读开只在内存迁移、不落盘；写开（resume/继续会话）发布 `session.v4.jsonl.zstd` 后继，源旧代文件保留且逐字节不变。执行步 = 逐会话写开，或接受按需惰性迁移；之后抽样打开验证，并留"仍为旧格式的会话清单"。
- 损坏与备份形态的会话文件先定处理规则（跳过、隔离或报错），不得让个别坏文件阻塞批量迁移。
- 附件与 storages 的恢复面判定（2026-09-24 C0 ⑦ 已核实）：**附件属于**，冷备纳入 `attachments/`（可排除派生的 `request-images/` 与空 `tmp/`）；**storages 不属于**（投影缓存，会话日志才是真源）。

**接口异步化迁移**

- 2026-09-24 C0 核实：rc.1 的 `snapshotEvents` / `eventAt` / `ownEvents` 同步读取签名与 0.1.5-rc.2 逐字相同，仅新增 `@deprecated`；存量调用可保留，宿主升级不因此阻塞。本决策所需的"确切签名"即 rc.1 现状（证据 `evidence/02-preflight-signatures.txt`）。
- 后续若要迁移到异步替代面（`ctx.sessionQuery` 等），逐处迁移、只替换读取路径，不借机重构；迁移完成后，单测与组合闸门两种 Profile 形态都必须全绿。

**Preset 载体**

- 仓库目录保持唯一真源；目标载体为与上游同构的声明形态（在插件组合包中声明一条 Preset 行），旧目录形态仅在取证确认仍被支持时作为过渡。
- 同步工具改造为"生成 Profile 侧产物"，并在写真实部署位前支持 dry-run。
- 该改造是迁移第一工作项；Team Profile 的 Preset 叠加实测依赖它。

**子代理锚定（方案 A，2026-09-25 裁决）**

- 子代理（`delegationDepth > 0`）豁免 minimal-plus 首轮锚定：`tool-bootstrap` / `phase-swap-bash` / `instruction-hint` 三处 `includeSubagents` 统一为 `false`，子代理首轮即全量工具目录。
- 主会话首轮锚定语义不变（`includeSubagents` 只分支子会话，见 `compaction-epoch.mjs` `status()`）；phase-swap-bash 硬编码 `includeSubagents: true` 改为读配置，复核子代理 swap/提权时机与 `tool:*` section 过滤一致性。
- 执行落在 0.1.7 的 Preset 生成形态上（票据 14），与「Preset 载体」同批收口。

**Team**

- Team 以单独 Profile 承载；非 Team Profile 不挂 Team 组合，保持普通委派与模型选择的可用性。
- 建立 Team Profile 之前必须先完成 Preset 叠加实测：先用哨兵行证明 Preset 真正生效，再观察普通委派工具是否与 Team 的创建工具并存、路由发现工具是否出现。
- 实测优先在真 PTY 冒烟上承载（可参数化 Profile 与 Preset、使用 stub provider、不需要真实模型），进程内假模型 harness 作为对照；两者都需新增 Team 组合的接线。
- 不可测时的回退：Team Profile 不让自研 Preset 下沉，票面记录"未测"，不写"推断为并存"。
- Team 会话的工具面按 Profile 单独快照；显示层不得用"工具是否存在"判断权限。

**闸门基准**

- 宿主钉版与会话格式版本断言随宿主切换同步更新（两者都不可豁免）。
- 一致性判定分两层：仓库与清单不一致属失败、不可豁免；部署位滞后属可豁免，且仅在声明的过渡窗口内豁免，收口时从调用链移除。
- 工具面期望按 Profile 维度重建；禁止整文件再生成，每个新增或移除的工具附行级差异与理由。
- 真实模型基线在新宿主上重采；旧基线保留为历史不删除；窗口内无法采集时显式记录"新宿主未跑"，不做跨宿主对比。
- 收口定义清单化：P0 项逐条有命名命令与归档证据、两种 Profile 形态闸门全绿、期望差异人工审阅、迁移完成并抽样、部署位与清单一致、各阶段失败即停并退回上一已验收状态。

**部署与回滚**

- Preset 产物与 Team Profile 在收口后一起落部署位；在此之前不动部署位。
- 回滚优先恢复本地保留的旧版本包与冷备；必要时再从仓库重装旧版本。

**节奏政策**

- 日常宿主跟稳定版；预发布只在临时前缀做侦察、不上日常入口；每出现一个新稳定版，按同一取证模板做只读取证并在固定窗口内升级。

## Testing Decisions

**什么算好测试**

只断言外部可观察行为：模型可见的工具集合、会话记录中的事件与请求头快照、闸门报告中的清单状态与版本断言、Preset 产物与真源的指纹一致性。不断言内部函数调用顺序、不依赖私有结构、不把实现细节写进断言。

**测试 seam（少量、取高处）**

- **取证 seam（新增，形式为临时前缀安装）**：目标版本的真实安装产物，用于签名、读写行为与兼容性事实；不进入仓库、不碰真实用户目录。
- **组合与闸门 seam（既有，主 seam）**：沿用既有回归闸门分层（静态层、零 LLM 组合层、假模型行为层；真实模型层按需），覆盖组合装配唯一性、首轮锚定、二轮放行与 bash 换用、部署位一致性与宿主钉版。
- **Preset 载体 seam（既有）**：仓库根 Preset 启动冒烟加部署位冒烟，证明生成产物可加载且与真源一致；同步工具的 dry-run 输出作为同一 seam 的前置检查。
- **Team 叠加 seam（既有构件、新增接线）**：真 PTY 冒烟（参数化 Profile 与 Preset、stub provider）读 Team Profile 的实际工具面；进程内假模型 harness 作对照。
- **真实模型 seam（既有，按需）**：真实模型探针在新宿主上重采基线后运行；窗口内不采集就显式记录未跑。

**被测模块**

自研 Preset 插件的行为（首轮锚定、指令提示、bash 换用、技能检索、Windows 分支）经组合冒烟；会话读取路径与回退插件经单测与组合冒烟；闸门清单与工具面期望；Team Profile 的工具面经叠加 seam。

**先例**

既有回归闸门与真 PTY 冒烟、既有真实模型探针与同口径批次工具、既有"装配工具集合加注入事件加请求头快照"的断言形状；新测试沿用同一形状，不另创断言风格。

**不做的测试**

交互终端体验不自动化（作为人工验收）；真实 provider 网络调用不进默认单测；不为跨宿主兼容写双分支测试。

## Out of Scope

- TUI 功能切片：子代理会话显示与折叠、收尾通知呈现、Team 成员视图与任务板、Team 使用规范文档——归功能计划。
- 自研 Preset 的瘦身与退役（本轮保留，只留事件触发复评条件）。
- 稳定树与另一支旧安装点的升级。
- Windows/pwsh 双栈改造。
- relay、长期记忆、worker 的代码适配；若升级清单中的远端接口项经取证判定为必须，另立票据。
- 跨版本兼容分支与版本探测。
- Team 实验性能力本身的上游加固（上游行为变化不在本轮控制范围）。

## Further Notes

**版本事实来源（第一方）**

- 逐版 release notes（GitHub 标签）与 npm dist-tags；其中一个中间版本没有 release，只有标签与包。

**不可逆边界**

- 会话日志迁移到 V4 后旧宿主不可读；冷备是唯一退路，且只覆盖快照之前的历史。丢失窗口与保留期必须在迁移票面落字。

**未取证事实（不得当作结论）**

- 迁移工具是否存在及其形态；新宿主对旧格式会话的读写行为；旧目录 Preset 是否仍加载；异步替代接口签名；无文档版本的变更面；附件是否属于恢复面。

**Preset 保留的依据与复评**

- 保留依据是不可替代的二轮提权行为；原始"让某模型更强"的假设没有实证，不作为理由。复评条件：上游出现等价提权路径、叠加实测证明委派行在 Team 下是死行、或实测证明模型选择从未被使用。

**Team 的已知限制**

- 队友共享同一工作区，无隔离与锁；预期写范围只是提示；成员状态不代表任务完成。这些限制进入使用规范文档（功能计划）。

**流程与发布**

- 本仓库未配置 issue tracker 与标签词汇；按既有惯例，spec 与后续票据以仓库文档形式发布，阶段与批准状态记录在流程状态文件中。
