# dsh-plugins local TUI 升级至 dsh 0.1.5-rc.1 并采用官方子代理模型选择

## Problem Statement

自研 TUI 目前运行在 dsh `0.1.1-rc.2` 上。上游已推进到 `0.1.5-rc.1`，其中多项变更会让现有代码在新宿主上无法启动或运行：会话事件读取接口被移除、会话持久化改为生命周期持有、agent 创建变为异步、会话格式升级到 V3 且不可降级读取、persona 配置拆分为前缀与后缀、插件侧代理上下文与 Inbox 接口收紧。

与此同时，使用者需要一个此前无法表达的能力：为不同的子代理指定不同的模型。旧宿主下官方委派工具既不暴露模型字段、也没有任何受控的路由来源，而角色化（按用途固定模型）需求又容易演变成一套自研路由层。

此外，组合配置长期与宿主重复：preset 逐字复制了宿主已有的十余行挂载，已经出现同一段提示正文在两处不一致的静默漂移，而两份配置无人对账。

最后，稳定 profile 被刻意钉在旧宿主版本上，因此它与开发 profile 不能再共享同一份组合配置。

## Solution

把开发侧（`tui-dev`、`tui-central`）升级到 `0.1.5-rc.1`，稳定侧（`tui` 及其隔离运行时）保持钉版不动；为开发侧分出独立的组合配置，使两个宿主的字段差异不再互相牵制。

子代理模型选择直接采用官方机制：由部署基线与用户设置共同给出一组允许路由，开启后模型可在其中为子代理指定 provider、model 与 reasoning effort，该策略记入会话并由子会话继承，且后续设置编辑不会改写已记录的策略。不再引入角色化命名、自研解析层、自研委派适配器，也不自建回退与覆盖事件。

组合配置收敛为"只声明与宿主的差异"：模型可见工具由宿主提供，组合层只保留确需不同的行。稳定侧继续使用原组合，开发侧使用新组合。

升级按阶段推进并保留回滚点：先记录版本与备份，再升级宿主、分叉组合、迁移代码、接入模型选择、去重组合，最后以同口径批次实验验证行为未回归。

## User Stories

1. 作为 TUI 使用者，我希望在升级后的宿主上正常启动 TUI，以便继续日常工作。
2. 作为 TUI 使用者，我希望恢复既有会话时能读取升级后的会话格式，以便不丢失历史上下文。
3. 作为 TUI 使用者，我希望升级过程保留原始会话文件，以便出问题时仍有退路。
4. 作为 TUI 使用者，我希望升级后的会话记录不会因为回退旧宿主而损坏，以便明确知道回退的边界。
5. 作为 TUI 使用者，我希望既有的交互能力（模型切换、回退、审批、压缩、状态栏）在升级后保持可用，以便升级不降低体验。
6. 作为 TUI 使用者，我希望升级前的会话文件有备份，以便在迁移失败时可恢复。
7. 作为 TUI 使用者，我希望在删除会话时不会因为新格式而被拒绝或损坏，以便维护工作区整洁。
8. 作为使用者，我希望为子代理指定模型时可以从当前可用的路由列表中发现候选项，以便不必凭记忆输入模型标识。
9. 作为使用者，我希望在创建子代理时指定 provider 与 model，以便让不同任务跑在不同模型上。
10. 作为使用者，我希望还可以为子代理指定 reasoning effort，以便在同一模型上调节推理强度。
11. 作为使用者，我希望省略模型选择时子代理继承调用方的路由，以便默认行为保持可预期。
12. 作为使用者，我希望子代理只能在我允许的路由集合内选择，以便模型不会把任务发到未经验证的端点。
13. 作为使用者，我希望允许路由集合能由部署基线和用户设置共同决定，以便不同运行模式有不同策略。
14. 作为使用者，我希望允许路由的改动只影响之后创建的会话，以便正在进行的会话不被中途改变。
15. 作为使用者，我希望一个会话一旦记录了允许路由，后续编辑设置不会改写它，以便同一次工作有稳定可解释的模型来源。
16. 作为使用者，我希望允许路由策略能被子会话继承，以便委派链上的模型来源一致且可追溯。
17. 作为使用者，我希望在没有记录策略的旧会话上该能力保持关闭，以便升级不会静默开启新行为。
18. 作为使用者，我希望 fork 出来的子代理与父会话保持同一路由，以便继承的历史仍可复用缓存而不被路由切换打断。
19. 作为使用者，我希望被工具过滤的子代理不会收到不可用工具的指导，以便子代理的工具面与其提示一致。
20. 作为使用者，我希望模型在明确不支持该能力时直接失败而不是静默忽略，以便配置错误尽早暴露。
21. 作为维护者，我希望组合配置只声明与宿主的差异，以便同一事实只有一处定义。
22. 作为维护者，我希望删除重复挂载后模型可见的工具集合保持不变，以便去重不改变行为。
23. 作为维护者，我希望去重后若有工具集合差异，每个差异都有可解释的原因，以便区分"预期变化"与"回归"。
24. 作为维护者，我希望稳定 profile 与开发 profile 使用不同的组合配置，以便钉版宿主不被开发字段破坏。
25. 作为维护者，我希望稳定侧的文件、运行时与组合配置完全不被本轮触碰，以便升级风险被限制在开发侧。
26. 作为维护者，我希望组合层里保留的每一行都有明确理由，以便下一个维护者知道为何不删除它。
27. 作为维护者，我希望术语表覆盖本轮引入与废弃的词汇，以便文档与代码使用同一套语言。
28. 作为维护者，我希望已废弃的设计方向被显式记录，以便不再被重新提出。
29. 作为维护者，我希望升级目标的版本事实有第一方来源记录，以便后续核对差异时不必重新调研。
30. 作为维护者，我希望有一组可重复的行为基线，以便判断升级与去重各自造成了什么变化。
31. 作为维护者，我希望行为基线的测量口径与历史批次一致，以便结果可与历史数据比较。
32. 作为维护者，我希望基线分两步采集（仅升级、升级加去重），以便区分两个变量的影响。
33. 作为维护者，我希望首轮锚定率、二轮注入与沙箱 bash 换用这三项在升级后不回归，以便核心交互质量有量化保证。
34. 作为维护者，我希望升级宿主时明确处置依赖该宿主的其他运行模式，以便它们不会以半坏状态反复重启。
35. 作为维护者，我希望升级与回滚的命令被记录在案，以便任何一次变更都可逆。
36. 作为维护者，我希望本轮不产生任何自动提交，以便改动在你审阅后由你决定去向。
37. 作为维护者，我希望验证不依赖未经验证的路由，以便"哪些路由真能工具调用"这件事有明确答案。

## Implementation Decisions

**目标与范围**

- 升级目标为 dsh `0.1.5-rc.1`（官方 `next` 标签），通过全局宿主生效；稳定侧的隔离运行时保持 `0.1.1-rc.2`。
- 本轮只覆盖开发侧（`tui-dev`、`tui-central`）的自研 TUI；relay、长期记忆、worker 的代码适配不在其中。

**组合配置分叉**

- 稳定侧继续使用既有组合；开发侧新建独立组合标识，承载新宿主的字段，并由 `tui-dev` 与 `tui-central` 指向它。
- persona 字段随之迁移：组合行的 persona 正文键改为前缀键，宿主级部署 persona 配置也改为前缀与后缀两键。
- 稳定侧的组合文件、隔离运行时与 profile 配置在本轮完全不动。

**子代理模型选择**

- 采用官方机制，在工作模式使用的委派工具配置上开启模型选择。
- 允许路由的来源为两层：部署基线给出初始集合，用户设置可覆盖；两者都表达为精确的 provider 与 model 组合。
- 模型可见的委派工具因此获得可选的 provider、model 与 reasoning effort 字段，并注册一个路由发现工具。
- 委派工具保持既有名称与两种上下文来源（全新子代理、继承父上下文），二者的差异只在上下文来源，不在路由策略。
- 不引入角色化命名（如按用途固定模型），因此不产生自研解析层、不自建委派适配器、不自建回退事件、不自建会话覆盖事件、不新增覆盖命令。
- 路由发现工具在同一工具作用域内只能由一个委派工具实例拥有，因此只为其中一个实例开启本能力。
- fork 来源的委派与宿主默认对齐：保持一次性运行且不参与模型选择，理由是与父会话保持同一路由、继承历史仍可复用缓存。它是否需要可持续运行属于独立议题，不在本轮评估。

**组合去重**

- 模型可见工具以宿主层提供；组合层只保留与宿主确有差异的行，删除逐字重复的行。
- 删除后为空的组合分组一并移除；仍需保留的分组只保留表达停用意图的行。
- 两行差异予以保留：始终禁用的 bash 行（该 agent 的 bash 由持久 shell 与换用后的沙箱 bash 提供）、以及承载模型选择开关的委派工具行。
- 两项原本的差异经本轮决定改为跟随宿主（网页抓取开关、计划模式提示正文），随即成为重复项，一并删除。
- 去重不得改变模型可见的工具集合；差异必须逐项解释。

**代码迁移**

- 会话事件读取改为按需快照与按下标取事件，不再读取已移除的事件数组。
- agent 创建按异步接口等待完成后再继续。
- 不构造 Inbox 运行时对象、不使用已移除的插件侧代理上下文、不依赖旧持久化方法。
- 会话格式升级为 V3 后不提供降级读取；升级流程以备份作为退路。

**升级副作用处置**

- 升级全局宿主会连带影响同样依赖它的其他运行模式：在升级时将其显式停用并记录恢复条件，避免以半坏状态运行。

**验证方法**

- 以同口径批次实验作为唯一行为 seam，分两步采集：仅升级、升级加去重；样本量与历史批次一致。
- 采集口径与历史批次逐字一致，记录字段不变。
- 该批次的测量工具需先完成与会话接口迁移相同口径的改造，且不借机重构。
- 配置层以配置导出作为门禁，证明装配与挂载正确，不用于行为断言。
- 既有单元回归保留。

**交付与提交**

- 本轮产出为文档与计划；不自动提交、不自动推送。

## Testing Decisions

**什么算好测试**

只断言外部可观察行为：模型可见的工具集合、会话记录中的事件与请求头快照、注入内容、子代理的最终路由。不断言内部函数调用顺序、不断言私有结构、不把实现细节写进断言。

**测试 seam（尽可能少，取最高处）**

- **行为 seam（唯一）**：以真实模型跑一批 headless 会话，会话挂载目标组合，从会话记录与装配结果中断言。它覆盖工具目录、首轮锚定、第二轮注入、bash 换用与子代理模型选择，是离"模型真实所见"最近的一处。
- **配置门禁**：对开发侧 profile 导出配置，证明模型选择设置服务与允许路由已就位、挂载行无冲突。只作前置门禁。
- **单元回归（既有，保留）**：组合层各插件沿用既有的假上下文测试；TUI 与回退插件沿用既有的 `node --test` 用例，覆盖会话接口迁移。

**被测模块**

组合层的首轮锚定、指令提示、bash 换用、技能检索、Windows bash 分支；TUI 的会话读取路径与回退插件的 fork/flush 路径；委派工具的路由选择（经由行为 seam 而非单测）。

**先例**

本仓库已有同口径的 headless 批次工具与其驱动脚本，以及按"装配工具集合 + 注入事件 + 请求头快照"断言的既有实践；新测试沿用同一形状，不另创断言风格。

**不做的测试**

真实 provider 的网络调用不进入默认单元测试；交互终端体验作为人工验收项，不自动化。

## Out of Scope

- 角色化（按用途固定模型）表达、自研解析层、自研委派适配器、自建回退与覆盖事件、覆盖命令。
- relay、长期记忆、worker 的代码适配；relay 协议变更。
- 稳定 profile、稳定运行时、稳定组合配置的任何改动。
- 依赖该全局宿主的其他运行模式的适配（本轮仅显式停用并记录恢复条件）。
- 实验性 Agent Teams；Web 侧的侧边栏、文件交付、面板 API；MCP 能力变更。
- 旧宿主兼容分支与版本探测。
- Windows 行为。
- fork 子代理是否应可持续运行的评估。

## Further Notes

**版本事实来源（第一方）**

- release notes：`https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.5-rc.1`
- 包元数据：`https://registry.npmjs.org/@deepseek-ai%2fdsh`（`next` 指向 rc.1；`latest` 仍为 `0.1.2-rc.1`）
- 破坏性字段以包内类型声明核实：persona 前缀与后缀拆分、宿主级 persona 双键、会话事件接口变化、委派工具新增模型选择开关与其子路径设置模块。

**作废的旧结论**

升级到 rc.1 之后，此前围绕"自研角色路由 + 自研委派适配器"形成的整套设计（含其回退事件、会话覆盖事件、覆盖命令、能力对照测试门槛）整体作废，见 ADR-0001。任何按旧结论推进的实现都应停止。

**已知风险**

- 允许路由若一次性列入全部已声明模型，会包含尚未验证工具调用能力的路由；已知某些密钥下同名模型会在工具调用时报错。验收环节需对每条允许路由做一次真实工具调用探测，未通过者应从允许集合移除。
- 会话格式升级后旧宿主无法读取，备份是唯一退路。
- 上游 rc 版本仍可能继续调整接口；本组合层不保留跨版本兼容分支，因此后续升级仍需同口径验证。

**测量数据现状**

历史批次中的两个对照分组所依赖的组合已被删除，仅剩开发侧分组可重跑；历史数据作为趋势参考而非严格对照，因为宿主版本已变。
